# handover（引き継ぎ書生成）

現在の会話全体を振り返り、次のセッションが読めば作業を再開できる引き継ぎ書を生成・保存する。

## 引数

- `$ARGUMENTS`（省略可）: 引き継ぎ書に含めたい補足情報・特に強調したい論点

## 手順

### Step 1: 会話文脈の整理

これまでの会話全体を振り返り、以下を洗い出す。憶測で埋めず、実際に会話・ツール結果に出てきた事実のみを使う。

- 背景・目的（何のためのタスクか）
- 完了した作業（変更したファイル、実行したコマンド、作成した PR・issue・commit）
- 未完了タスク・残課題
- 重要な決定事項とその理由（設計判断・トレードオフ）
- 関連リンク（PR、issue、Notion、ドキュメント等）
- 次に再開する人向けの具体的なアクション

### Step 2: 保存先の決定

まず現在の日付とプロジェクトルートを確認する。

```bash
date +%Y-%m-%d
git rev-parse --show-toplevel 2>/dev/null || echo "NOT_A_GIT_REPO"
pwd
```

次のルールで保存先ディレクトリを決定する。上から順に評価し、最初に該当したものを採用する。

1. `git rev-parse --show-toplevel` が成功し、かつ `<PROJECT_ROOT>/handover/` が**既に存在する**場合
   - → 保存先は `<PROJECT_ROOT>/handover/`
2. それ以外の場合（`handover/` が無い、または git 管理外）
   - → 保存先は `~/.claude/handover/<プロジェクト名>/`
   - `<プロジェクト名>` は、git リポジトリなら PROJECT_ROOT の basename、git 管理外なら `pwd` の basename
   - このディレクトリが存在しなければ `mkdir -p` で作成する

**重要**: ルール1は「ディレクトリが既に存在する」場合のみ該当する。存在しない場合にプロジェクト配下へ `handover/` を新規作成してはならない。会話要約には業務上の機微な情報が含まれうるため、リポジトリへ混入して意図せずコミットされるのを防ぐ。

ファイル名は `YYYY-MM-DD-<内容slug>.md`。

- `<内容slug>` はタスク内容を表す英数字・ハイフンの短い識別子（例: `ryde-pass-issue677`, `handover-skill-design`）
- 保存先ディレクトリを `ls` して、同名ファイルがあれば slug を変えて衝突を避ける

### Step 3: 引き継ぎ書の生成

以下のフォーマットで Markdown を作成する（frontmatter なし）:

```markdown
# 引き継ぎ書 YYYY-MM-DD — <セッション概要>

## 背景・目的

（何をしようとしていたか、なぜこのタスクが発生したか）

## 完了した作業

（変更したファイル・実行したコマンド・作成した PR/issue/commit を具体的に）

## 未完了タスク・残課題

（次に何をすべきか、ブロッカーがあれば明記）

## 重要な決定事項

（設計判断・技術選定とその理由。Codexとの壁打ち結果があれば含める）

## 関連リンク

- PR:
- Issue:
- Notion:
- その他ドキュメント:

## 次のアクション

（再開者がまず何をすべきか、具体的な手順）
```

`$ARGUMENTS` が指定されていれば、該当する内容を各セクションに反映する。

### Step 4: 保存・存在確認

Write で保存した後、必ず `ls` でファイルの存在を確認する。存在しない場合は再試行し、それでも失敗する場合はエラーを報告する。

### Step 5: 完了報告

- 保存したファイルのフルパスを報告する
- Step 2 のどちらのルールが適用されたか（プロジェクト配下 / 中央集約）も添える
- 手動運用の場合はこの後 `/compact` を実行してよい旨を伝える

## 注意事項

- 任意のプロジェクトで使えるグローバルスキルである。特定のリポジトリに依存しない
- 会話内容を正直に要約する。わからないことは「不明」「未確認」と明記し、憶測で埋めない
- 既存の `YYYY-MM-DD-<内容>.md` というファイル名規則を踏襲する
- git worktree では `git rev-parse --show-toplevel` が worktree のルートを返すため、中央集約先も worktree ごとに分かれる。作業内容が worktree ごとに異なる以上これは望ましい挙動なので、main リポジトリへの集約はしない
- 別リポジトリでもディレクトリ名（basename）が同じだと中央集約先が混ざる。その場合は slug でどのリポジトリの作業か判別できるようにする
